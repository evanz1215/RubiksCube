# 實作計畫：魔術方塊攻略網站

- 狀態：已實作（Phase 0–9 完成，待部署）
- 日期：2026-09-30
- 複雜度：高

## 需求

- 只做 3×3。使用者在 2D 展開圖或 3D 方塊上填色，驗證通過後在 Web Worker 算出 Kociemba、層先法、CFOP 三種解法，再用 3D 動畫加標準記號逐步播放
- 握法固定為黃上、綠前、白下；輸出只有 U D L R F B 六面轉動，沒有 `x`/`y`/`M`
- 單一頁面，方塊狀態存在網址，用 RWD 支援手機、平板和電腦，部署到 GitHub Pages

## 設計共識

### 範圍
- 只做 3×3，其他階數等 3×3 完成後再說
- 核心流程：輸入 → 驗證 → 解題 → 3D 動畫加步驟逐步播放
- 不做會員、儲存紀錄、多國語系、計時器；介面只有繁體中文，文字直接寫在元件裡
- 保留「隨機打亂」按鈕，同時拿來開發測試

### 技術
- 用 Vue 3、TypeScript、three.js（不用 TresJS，也不用 cubing.js 的 `<twisty-player>`，因為它不能自訂或點擊編輯貼紙顏色）
- 只有單一頁面，所以把 Router 拿掉
- 沒有後端，所有解法都在 Web Worker 裡計算
- 部署到 GitHub Pages
- 方塊狀態存在網址（`?s=...`），重新整理不會遺失，也能分享

### 方塊與握法
- 固定西方配色（白對黃、綠對藍、紅對橘），中心塊不能改
- 握法：白色朝下、黃色朝上、綠色朝前、橘色朝右（紅色在左），畫面上要明確提示

### 輸入
- 2D 十字展開圖和 3D 方塊都能點擊填色，兩邊同步
- 初始狀態除了中心塊全部是灰色，另附「填入已還原狀態」按鈕
- 2D 格子永遠顯示字母（W/Y/G/B/R/O），3D 上的字母可以開關
- 手機直立時上下堆疊（3D 在上、2D 在下、調色盤固定在底部）；平板和電腦左右並排

### 驗證（四層都做）
1. 每種顏色剛好 9 格：每填一格就即時檢查
2. 中心塊固定，對面配對正確
3. 每個角塊、邊塊的顏色組合真實存在：錯誤的方塊在 3D 和 2D 上都標紅框
4. 可解性（角塊扭轉、邊塊翻轉、排列奇偶）：只顯示文字，並建議使用者「檢查最近填的幾格」

第 3、4 層等全部填完才檢查，通過後「解題」按鈕才會啟用。

### 解法
三種一次算完，用分頁切換，每頁標出總步數。

- **Kociemba**：用 `min2phase.js`（MIT），約 20 步，不分階段
- **層先法**：自己寫，採七步法，白色十字直接在底面完成
- **CFOP**：參考 `rubiks-cube-solver`（MIT）自己重寫，跟層先法共用方塊模型；最後一層用完整 57 條 OLL 和 21 條 PLL，公式資料取自 `cubedex`（MIT，保留授權聲明）
- 層先法和 CFOP 的步驟按階段分組，每組有標題
- 只輸出標準記號；`x`/`y`/`M`/寬層轉動全部換算成 U D L R F B，使用者全程不用換握法

### 播放
- 上一步/下一步、自動播放/暫停、速度調整、點步驟直接跳轉、重播目前這步都有；手機上「下一步」按鈕最大
- 可以拖曳旋轉視角；有「重設視角」按鈕，每跳一步自動回到預設握法視角

### 測試
- 單元測試：方塊模型、驗證器
- 性質測試：跑 1000 組隨機打亂，三種解法的步驟都要能把方塊還原
- 一條 E2E：填色 → 解題 → 播放到最後一步

## 核心設計決策

| 項目 | 做法 | 理由 |
|---|---|---|
| 方塊狀態 | 54 格貼紙陣列，順序用 URFDLB（和 Kociemba 相同） | `min2phase` 可以直接吃；網址狀態就是這串字；只有這一種狀態格式 |
| 轉動 | 每個面的轉動寫成一張「貼紙位置對應表」，套用轉動時回傳新陣列、不改原本的 | 程式最少，也符合不可變原則 |
| 角塊/邊塊 | 需要時才從貼紙狀態推算出來（驗證和層先法/CFOP 會用到） | 不必同時維護兩套狀態 |
| 解法輸出 | `{ stage: string, moves: Move[] }[]`，三種解法共用；Kociemba 只有一個階段 | 分頁、分階段標題、播放器都只需要處理這一種格式 |
| 認出 OLL/PLL 和頂層情況 | 不寫辨識規則：把每條公式 × 4 種 U 層前置轉動都試套一次，看哪一組達成目標 | 57×4 次嘗試不到 1 毫秒，省掉一整套容易寫錯的圖形辨識表 |
| 安全網 | Worker 回傳前，把每種解法套回原狀態確認有還原；沒還原就回報錯誤、不顯示那一種 | 解法寫錯不會把錯誤步驟交給使用者照著轉 |

## 實作階段

每個階段結束時，都要能跑 `pnpm test:unit` 和 `pnpm type-check`。做完 Phase 6，只有 Kociemba 的版本就已經能用。

### Phase 0：清理與相依套件（低）
- 刪掉 Router 和 counter store；執行 `git init`（專案目前還不是 git repo）
- 安裝 `three`、`@types/three`、`min2phase.js`（安裝前先到 npm 確認套件名稱和 MIT 授權）

### Phase 1：方塊模型（中）
- 寫 `cube.ts` 的 18 種轉動（6 面 × 順時針/逆時針/180°）
- 寫 `notation.ts`：記號解析、反轉，以及整顆翻轉和中層轉動的換算（邊處理邊記錄目前的握法方向，把後面的面代號重新對應）
- 測試：同一面轉 4 次等於沒轉；一串轉動接上它的反轉等於沒轉；已知打亂套用後的貼紙字串要和其他工具算出的一致；換算前後的方塊狀態要完全相同

### Phase 2：驗證器（中）
- 四層驗證：各色 9 格、中心塊、角塊/邊塊組合、可解性（角塊扭轉總和是 3 的倍數、邊塊翻轉總和是偶數、角塊和邊塊排列的奇偶一致）
- 測試：每一種錯誤各寫一個案例（扭轉一個角、翻轉一個邊、交換兩個邊……），隨機打亂的狀態一律要通過

### Phase 3：Kociemba 與 Worker（中）
- `kociemba.ts` 加上 `solver.worker.ts`，Worker 一啟動就先做 `min2phase` 的初始化
- 性質測試：1000 組隨機打亂 → 求解 → 套回去必須還原

### Phase 4：3D 場景（高）
- 26 個小方塊加貼紙；用 OrbitControls 拖曳旋轉（three.js 內建的附加模組）；用 Raycaster 判斷點到哪一格
- 轉層動畫：把該層的方塊暫時掛到一個樞軸物件上，旋轉 90°，再把結果寫回貼紙狀態
- 可開關的字母標示；「重設視角」按鈕
- 在 jsdom 裡很難測 WebGL，這部分交給 E2E 截圖和手動檢查

### Phase 5：輸入介面（中）
- 展開圖、調色盤、點 3D 方塊填色，三者雙向同步；一開始除了中心塊全是灰色；「填入已還原狀態」和「隨機打亂」按鈕
- 每填一格即時檢查各色數量；全部填完再做組合和可解性檢查，把問題方塊在 3D 和 2D 上標紅框
- 網址 `?s=` 同步；手機上下堆疊，平板和電腦左右並排

### Phase 6：解題播放器（中）
- 解法分頁（標出步數）、分階段步驟清單、上一步/下一步/自動播放/速度/點步驟跳轉/重播這一步
- 每跳一步自動重設視角；手機上「下一步」按鈕最大
- 這時就是可以上線的 MVP（只有 Kociemba）

### Phase 7：層先法（高）
在白色朝下的前提下做七步法：
1. 底層十字：每條邊用小範圍深度搜尋（6 步以內）歸位
2. 底層角塊：先把角塊移到目標上方，再重複 `R U R' U'`
3. 中層邊塊：左插和右插兩條公式
4. 到 7. 頂層十字、頂面全黃、頂層角塊歸位、頂層邊塊歸位：都用「試套公式 × 4 種 U 前置轉動」

性質測試：1000 組隨機打亂都要還原，而且每個階段結束時，該階段的目標都要達成。

### Phase 8：CFOP（高）
- 十字：深度搜尋，8 步以內
- F2L：每一組角塊加邊塊，只用 U、R、F、L、B 做深度搜尋，並搭配剪枝；如果搜尋超過時間或深度上限，就退回層先法的做法（先放角塊、再放邊塊）
- OLL 57 條、PLL 21 條：都用試套法
- 性質測試：同上，1000 組隨機打亂都要還原

### Phase 9：E2E 與部署（低）
- 一條 Playwright 流程：填入已還原狀態 → 隨機打亂 → 解題 → 播放到最後一步 → 確認方塊已還原
- 設定 GitHub Pages workflow 和 Vite 的 `base`

## 相依關係

Phase 1 → 2 → 3 → 5/6；Phase 4 → 5/6；Phase 1 → 7 → 8。Phase 4 可以和 Phase 2、3 同時進行。

## 風險

| 風險 | 等級 | 對策 |
|---|---|---|
| CFOP 的 F2L 搜尋在手機上太慢 | 高 | 限制可用的轉動、剪枝、設時間上限，超過就退回層先法的做法；Worker 本身不會卡住畫面 |
| 貼紙位置對應表或配色對應打錯一格 | 高 | Phase 1 的性質測試，加上 Worker 回傳前的還原檢查（兩道防線） |
| 換算 `x/y/M` 後輸出不對 | 中 | 測試「換算前後的方塊狀態完全相同」 |
| 3D 轉層動畫快速連點時錯亂 | 中 | 動畫一次只處理一個轉動，放進佇列依序播放；跳步時直接設定目標狀態，不播動畫 |
| `min2phase.js` 的面順序或輸出格式跟預期不同 | 低 | Phase 3 先寫一個對照測試確認 |
| 紅色和橘色在手機上難分辨 | 低 | 2D 永遠顯示字母，3D 可以開關字母 |

## 估時

- Phase 0–6（Kociemba MVP）約 3–4 天
- Phase 7–8（層先法和 CFOP）約 3–5 天，其中 F2L 最不確定
- Phase 9 約半天
